# Changelog

User-facing changes per release. The commits behind each one are recorded in
[`docs/releases/`](docs/releases/), generated by `bin/release-notes --save`.

## 3.1.1 - 2026-08-18

### Fixed

- **A scaffolded runner passed `--no-interactive` twice**, and kiro-cli rejects
  it - so every Run through a runner created by `bin/init-ecosystem` failed. The
  template strips the flag from the forwarded args now. Comes with contract tests
  over the template (a fake kiro-cli that records its argv), verified by mutation.

### Added

- Badges for the `degraded` and `skipped` run statuses: amber for a partial
  success, muted for one that was never attempted. Nothing here emits them yet -
  they are the vocabulary a runner needs to report an honest partial result
  instead of flattening it into success or failure.

## 3.1.0 - 2026-08-18

### Added

- **Backlog execution state.** The board gained **Running** and **Failed**
  columns, fed by a `state:` field in the item's own frontmatter and set through
  `POST /api/backlog/state`. The item never moves on disk, so its review note,
  its order and its history stay attached to the same path; `active` clears the
  field rather than writing a value that means "no value". An unrecognised state
  keeps the item on the board instead of hiding it.

  Not a port of the v2 columns of the same name: those were never populated -
  v2's collector only ever read `backlog/` and `backlog/done/`. This is the
  contract they were meant to have.
- **`backlog-reviewer` starter agent.** Reads ONE item, investigates it against
  the code, and writes a review note with what is actually true today, the
  smallest plan, the blast radius and the exact validation. Deliberately narrow:
  it never executes the item and never touches `autonomy` - approving is a human
  click in the dashboard, so the review step keeps existing. That completes the
  loop the UI already had: agent proposes, human approves, executor runs.

### Fixed

- Editing an item's frontmatter no longer reformats the document: the closing
  delimiter was matched with a greedy `\s*`, which ate the blank line before the
  body on every write. A round trip is now byte-identical, verified against a
  real server.

## 3.0.2 - 2026-08-13

### Changed

- **The support agent's playbook caught up with the product.** It was written
  before `bin/collect-diagnostics`, `bin/init-ecosystem` and
  `bin/install-starters` existed, before the Run button learned to disable
  itself, before `/health` became `/healthz` and before agents grew a
  `cli_name` - so it kept teaching the old manual path. Both the spec and the
  loaded prompt now know every shipped tool and the current semantics.
- **The local agent acts instead of advising.** Running on the machine that owns
  the problem it executes the fix, with the stance set by blast radius: reads
  and probes freely, writes into the ecosystem after saying what they will
  write, anything beyond that asks first, and never deletes. Over a chat DM,
  where it cannot execute, it gives the ONE command rather than a manual
  sequence.
- New `test_support_playbook.py`: the playbook drifting out of date is now a
  test failure, not something noticed months later by a confused user.

## 3.0.1 - 2026-08-13

A fix release built entirely from a field report: the user named the root cause
and suggested the fix, and both are here.

### Fixed

- **Terminal mode failed when a config's `name` differs from its filename.**
  kiro-cli resolves `--agent` by the `name` field inside the `.json` config,
  but the dashboard composed the command with the filename stem - so the
  terminal opened on "no agent with name X found" and fell back to the default
  agent. Agent discovery now also carries the config's internal name
  (`cli_name`), and the agent page CLI button, Console sessions and Pipe mode
  all launch kiro-cli with it. The dashboard's own identity (runs, logs,
  queue) stays keyed by the filename.
- **The Run button had the same name-mismatch bug on its own path.** The
  trigger endpoint now hands the runner the resolvable name as the
  `AGENT_CLI_NAME` env var while the positional argument stays the filename
  stem (it keys the run in `runs.db`). The scaffolded `run-agent.sh` uses
  `${AGENT_CLI_NAME:-$AGENT}`; custom runners that ignore the variable keep
  working unchanged.

## 3.0.0 - 2026-08-13

First stable release, and the first one shaped by an external install. Everything here came from someone
other than the author running it on their own machine.

### Fixed

- **JSON-native agents were invisible.** Discovery only scanned `.md` frontmatter,
  so an ecosystem whose agents are bare kiro-cli `.json` configs showed an empty
  dashboard. A `.json` carrying `name` + `tools` is now a first-class agent; an
  `.md` + `.json` pair still counts once.
- **Triggering a run on a fresh clone failed opaquely.** `run-agent.sh` /
  `run-scheduled.sh` belong to the observed ecosystem, not to this repo. The API
  now answers `503` naming the missing file, and the Run buttons render
  **disabled** with a tooltip instead of offering a click that can only fail.
- **`main` no longer tracks build output.** Committed `dist` churned on every
  build and went stale silently. The bundles now live on a generated `release`
  branch (`bin/make-release`), which is what the app registry entry points at,
  so a one-click install still needs no Node.
- **A run stamped in the future is never the "last run"** (clock skew, a UTC
  container, a bad seed). It used to render a negative relative time while other
  views disagreed.
- Agent cards in the Agents tab are clickable as a whole, matching Overview.

### Added

- **Starter agents and jobs** - `bin/install-starters`: `heartbeat` (every 15 min,
  verifies the server serves the app and the API reads your ecosystem, and gives
  the charts real data immediately), `log-hygiene` (weekly, compresses logs past
  the threshold and never deletes), plus the `failure-triage` and
  `dashboard-support` agents. The scheduled ones need no LLM.
- **`bin/init-ecosystem`** - scaffolds the runner scripts and installs a launchd
  or systemd unit so the dashboard survives a reboot. Re-runnable on a live
  install; `--force` backs your files up before refreshing.
- **`bin/collect-diagnostics`** - one paste-able, secret-free environment report.
- **Update check** - a version button in the header, comparing against the
  upstream `app.json`. It only calls out when clicked, and a failed check says so
  instead of claiming you are up to date.
- **`DASHBOARD_INCLUDE_AGENTS`** - an allowlist, for when the agents directory is
  shared with agents installed by other tools. Exclusions still win.
- **App-host settings** - under KiroCrew the backend gets a minimal environment,
  so recognized keys from the host's per-app `config.json` now override env.
- **Packaged as a KiroCrew app** - `app.json` manifest, ASGI backend on an auto
  port, `/health`, and a thin shell page that embeds the app same-origin so the
  WebSocket terminals and SSE streams keep working.
- **Backlog kanban reorder** - drag cards in the active column; the order
  persists in each file's frontmatter.
- **`dashboard-support` agent** - guided install locally, or troubleshooting over
  a chat DM with a bounded reply window (`bin/await-reply`).

### Changed

- Site-specific failure hints moved out of the code into
  `DASHBOARD_EXTRA_HINTS`, keeping the shipped hint list generic.
- `docs/DECISIONS.md` records two decisions that came from real bugs: a PTY needs
  an explicit `winsize`, and a future-stamped run is not the last run.

## 3.0.0-alpha.1 / alpha.2 (pre-releases)

Pre-releases of 3.0.0. Initial public shape: typed FastAPI backend over the ecosystem's own
artifacts (`runs.db`, `queue/`, `schedule.json`, agent specs), React frontend
with Overview, Agents, Board, Health, Supervisor, Logs and Console, real-time
via a single WebSocket channel, failure diagnosis, PTY terminals and pipe mode,
and the universal `bin/record-run` adapter.
